# 카카오톡 Mac "대화 내용 저장" UI 참조 (O1''' 조사)

> 조사일: 2026-08-26 / 카카오톡 **26.7.0** / macOS 14.5
> 방법: 앱 번들 현지화 문자열(`/Applications/KakaoTalk.app/Contents/Resources/ko.lproj/*.strings`,
> UTF-16LE) **정적 분석**. UI를 클릭하거나 앱 상태를 바꾸지 않았다(C1 읽기 전용).

## 핵심 정정 — 라벨이 설계서 가정과 다르다

설계서·SKILL.md는 메뉴 이름을 "대화 내보내기"로 가정했으나, 실제 앱에는 그런
라벨이 없다. 실제로는 **서로 다른 두 기능**이 있고 이름도 다르다.

| 우리가 원하는 것 | 절대 쓰면 안 되는 것 |
|---|---|
| **"텍스트 파일로 저장"** | **"채팅방 저장소에 저장"** |
| `Chatroom_Setting_Storage_Message_Save_Chat_Button_Title` | `Chatroom_Setting_Storage_Message_Export_Chat_Button_Title` |
| 설명: "대화 내용 중 텍스트 메시지만 파일로 저장됩니다." | 톡클라우드(유료 구독) 업로드. 미구독 시 `Export_Chat_Permission_Error_Alert_Title`("톡클라우드 시작하기") 다이얼로그가 뜬다 |
| 로컬 파일 산출 → A0'가 필요로 하는 경로 | 클라우드 업로드 — 로컬 txt가 안 나오고, 되돌리기 번거로움 |

`Export_Chat_*` 키 계열은 **전부 톡클라우드 쪽**이다. JXA에서 `Export`라는
문자열로 UI 요소를 매칭하면 유료 경로를 누르게 되므로, 반드시 한국어 라벨
**"텍스트 파일로 저장"** 으로 매칭할 것.

## 추정 UI 경로 (정적 분석 기반, 실기기 미검증)

```
채팅방 열기
  → 채팅방 설정            ("Chatroom_Setting_Title" = "채팅방 설정")
  → 대화 내용 관리          ("Chatroom_Setting_Storage_Title" = "대화 내용 관리")
  → 대화 내용 저장          ("Chatroom_Setting_Storage_Message_Save" = "대화 내용 저장")
  → [텍스트 파일로 저장]     ("..._Save_Chat_Button_Title")
```

같은 화면에 **"대화 내용 삭제"**(`Chatroom_Setting_Storage_Message_Delete`,
"현재 채팅방의 대화 내용이 모두 삭제됩니다.")가 **바로 옆에** 있다.
JXA 자동화에서 좌표 기반 클릭을 쓰면 이걸 누를 위험이 있다 — **좌표 클릭 금지,
반드시 접근성 요소 이름으로 매칭**할 것. 이건 되돌릴 수 없는 파괴적 동작이다.

별도로 `Chatroom_Message_Export` = **"대화내용 내보내기"** 라는 라벨도 존재한다
(위치 미확인 — 채팅방 목록 우클릭 컨텍스트 메뉴 또는 채팅창 더보기 메뉴 추정).
이쪽이 더 짧은 경로일 수 있으므로 실기기 확인 시 함께 볼 것.

## 진행/완료 판정에 쓸 문자열

| 키 | 문구 | 용도 |
|---|---|---|
| `Chatroom_Message_Export_Writing` | "대화 내용 내보내기 중입니다." | 진행 중 대기 |

## 오픈채팅방 지원 여부 — **확정: 지원됨 (2026-08-26)**

운영자가 대상 방(노션하는 교사톡😉)에서 실제로 실행해 파일을 얻었다.
오픈채팅방도 "텍스트 파일로 저장"이 정상 동작한다. 정황 증거였던 아래 분석은
결과적으로 맞았다.

### ⚠ 산출물은 .txt가 아니라 **.csv**다

메뉴 이름이 "**텍스트 파일로 저장**"이라 설계서는 txt를 가정했지만, 실제로 나오는
파일은 **CSV**다. 이름과 확장자가 다르다.

```
파일명: KakaoTalk_Chat_<방이름>_<YYYY-MM-DD-HH-MM-SS>.csv
저장 위치: ~/Downloads (기본. 저장 다이얼로그 없이 바로 저장된 것으로 보임)
인코딩: UTF-8 + BOM
형식:
    Date,User,Message
    2025-01-26 09:49:48,"닉네임","본문"
```

**txt 형식 A/B보다 다루기 쉽다** — 초 단위 타임스탬프가 그대로 있고, 오전/오후
변환이나 날짜 헤더 상태 추적이 필요 없다. 개행이 든 본문은 인용부호로 감싸여
표준 csv 모듈이 한 레코드로 읽는다.

### Date·User가 빈 자리표시자 행

내용도 시각도 없는 행이 섞여 온다 (실측):

| 본문 | 건수 |
|------|------|
| `메시지가 삭제되었습니다.` | 265 |
| `관리자가 메시지를 가렸습니다.` | 17 |

타임라인에 놓을 수 없으므로 A1에서 버리되, **파싱 실패로 세지 않는다** —
실패로 세면 파싱률이 부당하게 떨어져 §5 에스컬레이션이 헛돈다.

### 시스템 메시지는 구조로 판정할 것

입퇴장 행은 `Message == User + "님이 들어왔습니다."` 구조다(실측 2176건 전부).
**키워드 '포함'으로 판정하면 안 된다** — 실측 데이터에 "삭제된 메시지 너무 궁금한
것....."처럼 시스템 키워드를 포함한 **평범한 사용자 발언**이 실제로 있다.

### 전량 내보내기라는 점

내보내기는 증분이 아니라 **방 전체 이력**을 준다(실측: 2025-01-26 ~ 2026-08-26,
26,907건). 매 사이클 전량이 다시 들어오므로 **A2의 중복 제거가 증분화를 담당**한다.
실측에서 26,907건 중 2건만 진짜 중복이었고 나머지는 전부 신규였다(최초 적재).

## (참고) 조사 당시 미확정이던 정황 분석

- `OpenLink.strings` 전체에 export/저장 관련 **제약 문구가 하나도 없다**.
  Localizable/Report 포함 전 파일에서 "오픈채팅 + 저장/내보내기 불가" 형태의
  문구도 발견되지 않았다. → 오픈채팅방을 따로 막고 있지 않을 가능성이 높다.
- 다만 이는 **정황 증거**다. 문자열이 없다고 코드 레벨 분기가 없다는 보장은 없다.
  메뉴 자체가 비활성(disabled)으로 뜨는 경우는 문자열을 남기지 않는다.
- **확정 방법**: 실제 대상 오픈채팅방에서 위 경로를 열어 "텍스트 파일로 저장"이
  존재하고 활성 상태인지 눈으로 확인한다. 이게 V1' 착수 전 남은 유일한 관문이다.

## 산출 파일 형식

`kakao-parser`의 **형식 B**(`--------------- 2026년 8월 25일 월요일 ---------------`
날짜 헤더 + `[이름] [오후 2:40] 본문`)로 예상된다. 이 형식은 이미 파서에
구현되어 있고 2026-08-26 Mac 세션에서 합성 데이터로 파싱률 100% 확인됐다.
실제 내보내기 파일을 처음 얻으면 **형식이 실제로 B가 맞는지 대조**할 것.
